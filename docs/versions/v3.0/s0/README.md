## 1. The Core Architectural Mandate

Avni V3.0 addresses a fundamental limitation in speech synthesis systems: **the coupling of identity and performance/expression.**

In previous releases (V1.0 - V2.5), vocal identity was represented as a monolithic, persistent representation. While this successfully enabled both Text-to-Speech (TTS) and Voice Conversion (VC), it offered no explicit mechanism to vary **how** a voice expresses something (pitch modulation, temporal dynamics, intensity) while maintaining a strict guarantee of **who** is speaking.

The objective of V3.0 is to establish **identity/expression disentanglement**:

```text
                     PERSISTENT IDENTITY (Who is speaking)
                                    │
                        ┌───────────┴───────────┐
                        ▼                       ▼
                  Expression 1            Expression 2 (How they speak)
                     [Calm]                 [Energetic]
                        │                       │
                        └───────────┬───────────┘
                                    ▼
                          Output Sound Field
                    (Timbre invariant, Prosody variant)

4. Architectural Invariants Preserved
Any developer extending V3.0 must adhere to these four rigid invariants:

Timbre Isolation: Speaker embeddings must not contain or encode variable prosodic controls. Identity metadata resides in VoiceRepresentation; styling factors must enter independently.
Renderer Agnosticism: Core contracts must never depend on PyTorch, Hugging Face Hub IDs, or model-specific serialization routines.
Downstream API Stability: NAV controllers consume stable capability profiles. New expression controllers must be introduced via optional interfaces or configurations.
Zero Regression Budget: Every incremental shift in the voice adapter configurations must pass all 93/93 baseline tests without exception.
